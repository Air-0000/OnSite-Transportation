基于 **TESS NG** 微观交通仿真平台的港口集装箱水平运输调度算法与全自动评测提交系统。

在给定港区路网上，为一支集卡车队规划**任务分配**与**行驶路径**，使其在 3600 秒仿真时长内尽可能多地完成集装箱运输批次，同时避免拥堵、死锁与冲突罚分。

算法从场景的 OD（起讫点）需求出发，自动识别运输拓扑结构并匹配对应的调度策略，最终输出可供评测的调度产物。

## 问题定义

**输入**

| 文件 | 内容 |
|------|------|
| `task.csv` | 运输批次：起点、终点、数量、计划起止时刻 |
| `vehicle.csv` | 可用车辆数 |
| `Scene/gangqu1.tess` | 港区路网（TESS NG 格式） |
| `Shortest path.csv` | 预计算的全局点对点最短路表 |

**输出**（写入 `Output/`，即评测产物）

| 文件 | 内容 |
|------|------|
| `id.csv` | 车辆编号 |
| `operation_state.csv` | 每次装卸作业的车辆、路段、状态、时刻、等待/结束时间 |
| `penalty.csv` | 对顶（butt）与冲突（conflict）罚分计数 |
| `task.csv` | 回带的任务输入 |

**核心矛盾**：路网是**有向**的，且存在少数被大量 OD 共享的**咽喉路段**。车辆数上去以后，朴素的"人人走最短路 + 同时发车"必然在咽喉处形成对顶与 gridlock —— 车队规模越大，完成量反而越低。因此调度的重点不是"走得快"，而是**让车流在时间与空间上错开**。

## 工作原理

整体是一条四段式流水线，每段解决上面矛盾的一个侧面：

```
task.csv (OD 需求) ─┐
Shortest path.py  ─┤
                   ▼
 ⓪ 起点/终点参数化 ──► 反推 GLOBAL_START / GLOBAL_END（卷无关）
      │
      ▼
 ① OD 拓扑识别 ──► pair / ring / mixed / chain / ringpair
      │
      ▼
 ② 调度模式选择 ──► generic / ringseg / optimized
      │                （决定"哪辆车按什么顺序做哪些批次"）
      ▼
 ③ 路径规划 ──────► sp_dict 查表展开为完整节点序列
      │                （可选：动态咽喉识别改道）
      ▼
 ④ 出车节流 ──────► 逐车错峰发车
      │
      ▼
 TESS NG 仿真 ──► Output/*.csv
```

### 0. 起点 / 终点参数化（卷无关）

调度需要知道"所有车从哪出发、最后回到哪"——即 `GLOBAL_START` / `GLOBAL_END`。
过去这两个值是硬编码的（B卷为 `82` / `191`），换卷（如 C卷只有 1 个终点）就得改代码。

现在改为**自动反推**：

- `Shortest path.py` 里的 `target_id` **书写顺序**约定为 `起点 → 终点 → 装卸点`；
- **起点** = 顺序第 1 个节点；
- **装卸点** = 在当前场景 `task.csv` 中出现过的节点（origin/dest 并集）；
- **终点** = 书写顺序中「第一个装卸点之前」的连续节点块（即不出现在 task.csv 里的那几个）；
- **默认终点** = 最后一个终点。

> `target_id` 是 `set` 字面量，`ast.literal_eval` 会打乱顺序，故按**源码文本顺序**正则解析，
> 而非按集合迭代顺序。

解析失败、或当前场景没有任何装卸点出现时，**回退到 `(82, 191)`**，保证 v4 行为完全不变。
因此换 C卷（单终点）只需更新 `Shortest path.py` 的 `target_id` 与 `Scene/*.tess` 路网，**无需改算法代码**。

### 1. OD 拓扑识别

`od_classify.py` 把一组批次抽象成**有向图**（节点=作业点，边=批次），根据入度/出度分布判定拓扑类型：

| 类型 | 图特征 | 直观含义 |
|------|--------|----------|
| `pair` | 若干互为反向的边 | A⇄B 往返对运 |
| `ring` | 单个闭合环 | A→B→C→A 环形接力 |
| `chain` | 首尾相接的链 | A→B→C→D 单向链 |
| `ringpair` | 环 + 反向边 | 环形且双向 |
| `mixed` | 以上皆非 | 混合结构 |

拓扑决定了**空驶（deadhead）的下界**：链式/环式 OD 的终点恰是下一批的起点，理论上可做到零空驶；而 pair 型只能靠往返配对来消化。

### 2. 三种调度模式

识别结果映射到三种分配策略：

| 模式 | 适用拓扑 | 策略 |
|------|----------|------|
| `generic` | pair / mixed | **阶段式**分组：同一组车先全部跑正向、再全部跑反向 |
| `ringseg` | ring | 环拆成若干 2-链分段，组内前半正向、后半反向，首尾相接零空驶 |
| `optimized` | chain / ringpair | **拉丁方轮转 + 欧拉链**：第 t 轮车 v 承接批次 `(v+t) % nb`，沿欧拉路径铺开 |

> **`generic` 的关键约束**：必须是阶段式 `[正向全部, 反向全部]`，
> **不可**写成交错式 `[正, 反, 正, 反…]`。
> 交错会让同组车在同一路段迎头相撞，是历史上死锁的直接成因。

所有车辆统一以自动反推的 `GLOBAL_START` / `GLOBAL_END` 出发与收尾（B卷即 `82` / `191`），避免起终点本身成为新的冲突源。详见 [§0 起点/终点参数化](#0-起点--终点参数化卷无关)。

### 3. 路径规划

`Shortest path.csv` 是官方预计算的全局点对点最短路表，加载为 `sp_dict[(u, v)] -> [节点序列]`。
每辆车的任务序列（形如 `[82, o₁, d₁, o₂, d₂, …, 191]`）逐段查表展开、首尾拼接，得到完整行驶路径。

### 4. 动态咽喉识别

**默认关闭**，由环境变量启用。开启后在展开路径前插入一步改道：

```
① 建图      从 Shortest path.csv 的所有路径中抽取有向边，得到路网图 G
② 压吞吐    按本场景 OD 需求给边加权：edge_load[e] += 该 OD 的货运量
③ 定咽喉    choke = argmax(edge_load)，ratio = 该边吞吐 / 全场景总货运量
④ 阈值判定  ratio < THROAT_MIN_RATIO 则放弃改道（收益不足，不值得扰动）
⑤ 改道      对所有经过 choke 的 OD，在 G 中禁掉该边重跑 Dijkstra
            —— 找不到替代路径（该边是割边）则保留原路
```

这是**场景无关**的：咽喉不是写死的常量，而是每道题按自己的 OD 需求现算出来的。
不同题会得到不同的咽喉边，例如 `(200,177)`、`(201,99)`、`(291,188)`、`(271,83)`。

**为什么按货运量加权而不是按路径条数**：一条 OD 可能要跑 6 车次，另一条要跑 16 车次，
对咽喉的实际压力差了近 3 倍。用 `qty` 加权才反映真实吞吐。

**为什么用跳数做 Dijkstra 权重**：目标是"绕开这条边且尽量不多绕"，
最小跳数在本路网上与最短距离高度一致，且无需额外的边长数据。

> **两级作用域开关**：`AVOID_THROAT` 打开机制，`THROAT_SCENES` 进一步把它限制在指定题号上
> （需要调用方通过 `SCENE_ID` 告知当前题号，拿不到则保守关闭）。
> 这是必要的 —— 咽喉边在**所有**场景中都存在，无差别开启会改动每一道题的路径，
> 对已经调优的场景是纯风险。
>
> **实战中最安全的使用方式**：只开 `AVOID_THROAT=1`，**不填** `THROAT_SCENES`。
> 此时 `run_low_score.py` 会按 `THROAT_SCORE_THRESHOLD`（默认 1500）自动把白名单设为
> 「SSoT `score.csv` 里总得分低于阈值的低分题」——当前即 B15/16/20/26/40/43/67/69/71/73/74/75 共 12 题，
> 且这 12 题恰好都是咽喉占比 ≥0.30、改道确有空间、改坏也损失最小的题。
> **高分题（B2/B3/B4/B50/B52 等 6000+）永远不在白名单内，咽喉对其绝不触发**，从机制上杜绝回归。
> 若要更宽覆盖，调高 `THROAT_SCORE_THRESHOLD`（如 `2000` → 25 题）即可；手填 `THROAT_SCENES` 则优先采用你的设定。

### 5. 出车节流

即使路径错开了，若所有车在同一时刻涌入路网，咽喉仍会瞬时过载。
默认按组内序号发车（`send_t = 5 + within_group × BASE_INTERVAL`），
这会把大车队压缩成少数几个出发波次。
设置 `ASSIGN_STAGGER=<秒/车>` 可改为按全局车序均匀铺开（`send_t = 5 + v × STAGGER`），把波次摊平。

### 6. 时间窗感知（实验性）

**针对场景**：低分题里「任务未完成 + 任务超时」主导、而非拥堵的那一批
（实测 B15/16/20/26/40/67/69/71/73/74/75，11 题合计仅冲突扣分 ~-1164，
但 未完成 ~-7768、超时 ~-7451，合计 ~-15219；提前完成加分却很高 +1400~+2864，
说明多数任务已提前完成，仅少数批次未能在 20 分钟时限内送达）。

**根因（离线核查结论）**：这 11 题每批任务时限**统一 20 分钟**、同时峰仅 4~6 批、
60 车全量覆盖、每批货量 100% 已派到车上 —— 既不是拥堵、也不是派车缺口、也不是窗口过紧，
而是**部分批次的「起点→终点」最短路径行驶耗时超过其 20 分钟时限**，到得晚 → 超时/未完成。

**做法**：`TIME_WINDOW_AWARE=1` 时，在派单完成后、拼接起点/终点前，对**每辆车自身的停靠顺序**
按任务截止时间升序（最早截止优先，EDF）重排。**只改顺序、不改「谁做哪批」**，
因此派车覆盖量不变、不会凭空制造新的未完成任务；早截止批次先送 → 减少超时/未完成，
并把提前加分往前推（双收益）。默认关闭，v4 行为完全不变。

> **验证约束**：本机制为纯确定性重排，开启后必须走「staging 全量跑、对比 212,418.31 零回归」流程
> 才采纳；切勿直接覆盖已采纳结果。沙箱内 TESS 仅起 GUI 壳无真实仿真，须在实机验证。

## 快速开始

- **Windows**：TESS NG 已安装，Python 3.6 环境（含 `tessng` 包）
- **Linux**：使用提供的 Docker 镜像
- 依赖见 `requirements.txt`：`numpy==1.19.5` / `pandas==1.1.5` / `PySide2==5.15.2.1` / `tessng==4.1.1.0`

评测输入建议放在与本仓库同级的 `Test Paper B/B/B_B{n}_input/` 下（或由环境变量 `ONSITE_INPUT` 指定），每个场景包含 `task.csv` 与 `vehicle.csv`。

```
├── OnSite-Transportation/   # 本仓库
└── Test Paper B/B/
    ├── B_B1_input/{task.csv, vehicle.csv}
```

```bash
python main.py
```

以 `Scene/gangqu1.tess` 为路网启动一次仿真，读取 `Output/task.csv` 与根目录 `vehicle.csv`，产物写入 `Output/`。

## 使用流程

完整流程是 **跑 → 打包 → 上传 → 取分 → 对比 → 采纳**：

```
run_low_score.py  ──►  pack_submit.py  ──►  upload_curl.py  ──►  score.csv
   (批量仿真)            (打包 zip)          (上传取分)          (对比基线)
```

### 1. 批量重跑

```bash
python run_low_score.py             # 跑所有低于阈值(默认1500)的场景
python run_low_score.py --only 67   # 只跑 B67
python run_low_score.py --dry-run   # 只校验输入是否齐备，不启动仿真
```

脚本会逐题把输入拷到位、用 `subprocess` 串行拉起 `main.py`，产物写入 `test/new_test/B{n}/`。
内置看门狗：仿真时钟长时间不推进（`STALE_WALL`，默认 900s）时强制结束，防止卡死整批任务；到达总时长后交由 TESS 自然退出，不再强制收尾宽限。

> **必须串行**：TESS NG 是单实例的，并行启动会直接崩溃。

### 2. 打包

```bash
python pack_submit.py [结果目录]    # 默认 test/，产出 {目录}_submit.zip
```

产出扁平结构的 zip（`B1/id.csv`、`B2/id.csv` …），符合评测平台要求。

### 3. 上传取分

```bash
export UPLOAD_USER=<用户名>
export UPLOAD_PASS=<密码>
python upload_curl.py --zip <submit.zip> --volume B --out score.csv
```

也可用 `--user` / `--password` 直接传参。内部走 `curl` 以绕过证书校验问题。

### 4. 对比与采纳

**评分一律以平台返回的 `score.csv` 为准**，本地不做评分估算。
新方案必须全量跑完、与当前基线逐题对比**零回归**后才可采纳 —— 单题提升掩盖多题下滑是很常见的陷阱。

## 配置项

所有开关均通过环境变量控制，**全部不设时算法行为固定**（等价于经过验证的 v4 版本）。

### 算法开关

| 变量 | 默认 | 说明 |
|------|------|------|
| `AVOID_THROAT` | 未设置 | 启用动态咽喉识别与改道 |
| `THROAT_SCENES` | 空 | 逗号分隔的题号白名单（如 `67,26,69`），仅这些场景改道；需配合 `SCENE_ID`。**未显式设置时，`run_low_score.py` 会按分数自动生成白名单**（见下） |
| `SCENE_ID` | 空 | 当前题号，由 `run_low_score.py` 自动注入 |
| `THROAT_SCORE_THRESHOLD` | `1500` | **分数阈值（核心开关）**：`AVOID_THROAT` 开启且未手填 `THROAT_SCENES` 时，`run_low_score.py` 自动把白名单设为「SSoT `score.csv` 中总得分 `< 该阈值`」的低分题。**高分题（含 B2/B3/B4/B50/B52 等 6000+）一律不进白名单 → 咽喉机制对其永不发生**，避免回归 |
| `THROAT_MIN_RATIO` | `0` | 咽喉吞吐占比阈值，低于此值放弃改道（如 `0.35`）；白名单内仍按此做二次过滤 |
| `ASSIGN_STAGGER` | 未设置 | 整数「秒/车」，按全局车序均匀铺开发车时间 |
| `TIME_WINDOW_AWARE` | 未设置 | **实验性** 时间窗感知：仅重排「每辆车内部」停靠顺序为最早截止优先（EDF），不改派车覆盖。针对「任务未完成/超时」型低分题（B15/16/20/26/40/67/69/71/73/74/75 等）。详见 [§6](#6-时间窗感知实验性) |

### 运行时开关

| 变量 | 默认 | 说明 |
|------|------|------|
| `MAX_SIM_TIME` | `3600` | 仿真总时长（秒） |
| `RUN_TIMEOUT` | `7200` | 外层看门狗总超时（秒） |
| `STALE_WALL` | `900` | 仿真时钟停滞多久判定卡死（秒） |
| `KMP_DUPLICATE_LIB_OK` | `TRUE` | 抑制 OpenMP 重复库告警 |

**示例**：只对 B67 和 B26 启用咽喉改道，且要求咽喉吞吐占比至少 35%

```bash
AVOID_THROAT=1 THROAT_SCENES=67,26 THROAT_MIN_RATIO=0.35 python run_low_score.py
```

```dockerfile
FROM constant0000/track0409:stale-fix-v6
```


## 已知限制

- **TESS NG 单实例**：仿真必须串行，无法并行加速；单题耗时约 12–38 分钟。
- **内存占用**：24 车、30 车规模的场景峰值内存约 23 GB，低配机器会 OOM；14/18 车场景正常。
- **收尾退出**：仿真到达总时长后交由 TESS 自然退出（已取消强制收尾宽限）；若 TESS 在收尾阶段真卡死、仿真钟长时间不前进，`STALE_WALL`（默认 900s）看门狗会强制结束，产物已完整写出。
- **咽喉改道非普适增益**：咽喉边在所有场景中都存在，无差别开启会改动每一道题的路径。
  务必用 `THROAT_SCENES` 限定作用域，并以全量对比结果决定是否采纳。
- **路径改道基于跳数**：`Shortest path.csv` 不含边长，Dijkstra 以跳数为权重。
  绝大多数情况与最短距离一致，但极端拓扑下可能产生非最优绕行。
- **换卷无需改算法**：起点/终点已由 `Shortest path.py` 的 `target_id` 与场景 `task.csv` 自动反推
  （见 [§0](#0-起点--终点参数化卷无关)）。换 C卷只需更新 `target_id` 与 `Scene/*.tess` 路网，
  `GLOBAL_START` / `GLOBAL_END` 会自动取到对应值；解析失败则回退 `(82, 191)`，v4 行为不变。
